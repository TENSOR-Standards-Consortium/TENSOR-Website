### Graph Nodes and Edges  
TENSOR represents an investigation as a directed graph of **nodes** and **edges**. Each **node** corresponds to an investigative question (for example, "Is the file malicious?") and is identified by a unique ID (e.g. **Q1**, **Q2**, etc.). Nodes have a **text** field for the full question and a **category** indicating one of seven domains: Application, Cloud, Email, File, Host, Identity, or Network. Nodes may also include an optional short **label** for visual displays, and can support localized **translations** of the text/label for different languages. Each **edge** in the graph represents a branching path between two nodes, defined by a **source** node, a **target** node, and a **decision**. The decision describes the answer leading from source to target – it can be **"yes"**, **"no"**, or **"unknown"**. Edge IDs encode this format (for example, **Q12-yes-Q1** connects Q12 to Q1 on a "yes" decision). The graph format also allows an **extensions** object at the graph, node, or edge level for additional metadata (such as case-specific notes or tool-specific fields), ensuring the core schema remains flexible for different use cases.

### Loops and Repeated Questions  
Unlike a simple decision tree, the TENSOR graph can include **loops** (cycles) where a sequence of decisions leads back to a previous question. This allows the framework to revisit key questions for multiple related artifacts or scenarios within a single investigation. **Loops are explicitly permitted** in the standard. For example, in the core graph the question **Q12** ("Does the email contain a malicious attachment?") has a "yes" branch back to **Q1** ("Is the file malicious?"). This loop means that if an email attachment is found to be malicious, the investigation returns to the file analysis question (Q1) for that attachment. Such cyclical references let TENSOR avoid duplicating nodes and ensure that common investigative steps are **reused whenever applicable**.

### Investigation Domain Coverage  
The core set of TENSOR questions is designed to cover a broad range of incident aspects across the seven defined domains. By following the graph, an analyst can systematically traverse relevant questions about files, hosts, network activity, user accounts, emails, cloud resources, and applications. The open format means organizations can extend the graph with additional domain-specific or custom questions (under their own namespaces) while still maintaining compatibility with the core model. Cycles in the graph also help ensure **no important question is overlooked** – if one path of inquiry reveals new evidence (e.g. discovering another malicious file or a compromised account), the graph logic can circle back and prompt analysts to address those developments using the same standard questions.

### Using the TENSOR Standard  
TENSOR is an open framework meant to be adopted within investigation tools and workflows. Security platforms or SIEM/SOAR products can implement TENSOR’s schema and core graph to guide analysts through investigations in a consistent way. Because the framework is vendor-neutral, the same TENSOR-defined investigative steps can be shared across organizations and products. Analysts become familiar with a common investigation playbook (captured in the graph), and findings or decisions can be communicated using TENSOR’s question IDs and outcomes. Over time, the community may propose improvements or new nodes/edges to the standard, continually refining the investigative model. By integrating TENSOR, incident response teams and tools benefit from a **common, structured approach** to handling threats – making it easier to collaborate and to incorporate automated reasoning (like AI assistants) using the shared graph vocabulary.
